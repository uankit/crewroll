# CrewRoll E2EE Key Lifecycle

**Status:** Binding SEC-001 policy for MVP protocol version 1.

**Scope:** One random trip epoch key, immutable key epoch 1, native-only private material, no server-decryptable or cross-device escrow.

## Key hierarchy, sizes, purposes, and encodings

All random keys are generated by the operating system CSPRNG or libsodium `randombytes_buf`. No key, nonce, header, identifier, password, timestamp, media byte, or test fixture is used as random-key input.

| Name                                   | Algorithm / size                              | Lifetime                                                     | Storage and export rule                                                                                                                          |
| -------------------------------------- | --------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Device P-256 identity / future PoP key | ECDSA P-256 private key, non-exportable       | Device registration until device revocation/account deletion | iOS Secure Enclave where available; Android Keystore. Public key only may cross native/JS/API boundaries. Not used to authenticate MVP requests. |
| Device E2EE key                        | X25519 private/public, 32 bytes each          | Device registration until device revocation/account deletion | iOS Keychain; Android wrapped by the device KEK. Raw private key never crosses native.                                                           |
| Android device KEK                     | AES-256-GCM, 32 bytes, non-exportable         | App installation until device revocation/account deletion    | Android Keystore; wraps native secret records at rest.                                                                                           |
| Trip epoch key                         | Random 32 bytes                               | Trip creation/import through terminal retention cleanup      | Native secure storage only; epoch is exactly `1`.                                                                                                |
| Manifest protection key                | 32 bytes derived from trip key                | Per operation                                                | `crypto_kdf_derive_from_key`, context `CRMANF01`, subkey ID `1`; never persisted.                                                                |
| Asset content root                     | Random 32 bytes per asset                     | Asset encryption/decryption operation                        | Carried only inside the encrypted manifest; erase after durable ciphertext/manifest creation or exact save.                                      |
| Preview stream key                     | 32 bytes derived from content root            | One preview blob                                             | KDF context `CRROLL01`, subkey ID `1`; never persisted separately.                                                                               |
| Original stream key                    | 32 bytes derived from content root            | One original blob                                            | KDF context `CRROLL01`, subkey ID `2`; never persisted separately.                                                                               |
| Source-ID HMAC key                     | Random 32 bytes                               | App installation/account namespace                           | Native secure storage; used with HMAC-SHA-256 over the raw platform library identifier.                                                          |
| Background bearer                      | Opaque, server-generated, expiring credential | Until expiry, refresh, logout, or revocation                 | Native secure storage. It is authorization material, not an E2EE key.                                                                            |

### Canonical public encodings

- `authenticationPublicKey`: uncompressed ANSI X9.63/SEC1 `0x04 || X[32] || Y[32]`, exactly 65 decoded bytes.
- `e2eePublicKey`: raw X25519 public key, exactly 32 decoded bytes.
- Binary fields exposed through JSON use RFC 4648 standard Base64 with `+`, `/`, and required `=` padding. Decoders reject whitespace, URL-safe alphabet, omitted padding, non-zero unused pad bits, alternate spellings, and trailing bytes.
- UUIDs are validated before cryptographic use. Trip-envelope v1 serializes UUIDs as the 16 RFC network-order bytes in the trip-key envelope layout. Manifest/media AAD serializes UUIDs as lowercase 36-character hyphenated ASCII. These representations are structure-specific and never substituted for one another.
- Integers in binary cryptographic structures are unsigned 32-bit big-endian values.
- Key and algorithm versions start at `1`; unknown versions are rejected before cryptographic processing.

The current generic `Base64Schema` does not enforce these lengths. Tightening it is a downstream shared-contract change, not a reason for native code to accept ambiguous keys.

### P-256 identity-key scope

The P-256 key is provisioned because the locked architecture names device-authentication key material. The current MVP authorizes requests with Clerk/device bearers and does not define P-256 proof of possession. API-002 “forged key rejection” therefore means authenticated-account registration, exact structural validation, immutable installation/device/key-version binding, idempotent conflict rejection, and authorization through the issued device bearer; it does **not** prove possession of the P-256 private key. Before the key authenticates a request, a separately approved protocol must lock its domain separator, signed fields, server nonce/challenge lifetime, replay store, request binding, clock independence, signature encoding, and verification failure semantics.

## Trip-key envelope v1

### Outer wire object

The semantic outer object is exactly:

```text
keyEpoch:        1
algorithmVersion: 1
wrappedKey:      canonical padded Base64 of exactly 148 decoded bytes
```

`algorithmVersion = 1` means libsodium `crypto_box_seal` / `crypto_box_seal_open`, whose construction uses X25519 and XSalsa20-Poly1305 and adds 48 bytes to the plaintext. It provides recipient confidentiality and ciphertext integrity, but not cryptographic sender authentication.

### Sealed plaintext

Before sealing, native constructs exactly 100 bytes in this order:

| Offset | Bytes | Value                                                    |
| -----: | ----: | -------------------------------------------------------- |
|    `0` |     8 | ASCII domain `CRTKENV1`                                  |
|    `8` |     4 | algorithm version, uint32 big-endian, value `1`          |
|   `12` |    16 | trip UUID parsed to RFC network-order bytes              |
|   `28` |     4 | key epoch, uint32 big-endian, value `1`                  |
|   `32` |    16 | sender device UUID                                       |
|   `48` |    16 | recipient device UUID                                    |
|   `64` |     4 | recipient E2EE key version, uint32 big-endian, value `1` |
|   `68` |    32 | random trip epoch key                                    |

The sender calls `crypto_box_seal(payload, recipientX25519PublicKey)`. The result is exactly 148 bytes (`100 + 48 = 148`) and Base64-encodes to exactly 200 ASCII characters with required padding.

### Validation and idempotency

`importTripKey` must:

1. Reject a noncanonical Base64 value, any decoded length other than 148, and any outer algorithm/epoch other than 1.
2. Use only the local recipient X25519 key version declared by the command and secure vault.
3. Fail closed if sealed-box authentication fails.
4. Require exact domain, algorithm, trip ID, epoch, expected sender device ID, local recipient device ID, and local recipient E2EE key version matches.
5. Persist the 32-byte trip key in secure storage only after every check succeeds.
6. On replay, succeed only if the already-stored trip/epoch key is byte-identical. A different authenticated key for the same trip/epoch is `KEY_ENVELOPE_INVALID`, never replacement.
7. Erase plaintext parse buffers and temporary keys after persistence or failure.

`wrapTripKey` must read the already-stored trip key, validate the exact 32-byte recipient public key, seal a new randomized envelope, and return the full algorithm/epoch/wrapped-key tuple. Two valid envelopes for the same inputs normally differ because sealed boxes generate an ephemeral key pair.

The sender device ID inside v1 is context binding, not proof of sender possession. API authorization proves which enrolled owner submitted an approval under the MVP trust model; the sealed box alone does not.

Because the recipient public key is public and sealed boxes are anonymous, any party can construct a new cryptographically valid, context-correct envelope containing a different trip key. On first import v1 cannot distinguish that replacement from the owner's envelope. The resulting split key causes genuine manifests/media to fail authentication and is treated as a key-authenticity/availability incident; it does not reveal genuine plaintext. If a valid key is already installed, the conflicting import is rejected. Preventing first-import substitution requires verified sender signing/key transparency and is outside MVP.

### Owner envelope

The owner follows the same rule as every recipient: create one random trip epoch key locally and seal it to the owner's own X25519 public key. There is no plaintext owner shortcut and no server-generated trip key.

This requires the client to know the final `tripId` before producing `ownerKeyEnvelope`. The accepted HTTP schema currently requires the owner envelope while the server assigns/returns the trip ID; this is a blocking downstream contract contradiction.

`createTripKey` initially stores the owner key as `PROVISIONAL` with `createdAt` and `provisionalExpiresAt = createdAt + 24 hours`. After a successful create response, the client passes the returned owner envelope through `importTripKey`; an exact match transitions the record to `INSTALLED`. A definitive server rejection or user cancellation before a server trip exists calls `discardProvisionalTripKey({ tripId, keyEpoch: 1 })`. A timeout/disconnect is an unknown outcome, so the key is retained while the same idempotency key is retried; it is not discarded on transport uncertainty. Native cleanup deletes only still-`PROVISIONAL` records at/after `provisionalExpiresAt` on launch, foreground, and scheduled reconciliation. If the server committed but the response was lost and the provisional record later expires, the same device can recover from the server-held owner envelope while its X25519 key survives.

## Asset keys, manifest protection, and media framing inputs

### Asset hierarchy

For each logical asset:

1. Generate one random 32-byte content root.
2. Derive preview key: 32 bytes, KDF context `CRROLL01`, subkey ID `1`.
3. Derive original key: 32 bytes, KDF context `CRROLL01`, subkey ID `2`.
4. Independently initialize secretstream for preview and original, producing distinct random 24-byte headers.
5. Protect the canonical manifest plaintext, which contains the content root and all private metadata, with a manifest key derived from the trip epoch key using context `CRMANF01`, subkey ID `1`.

Manifest protection v1 uses `crypto_aead_xchacha20poly1305_ietf` with a fresh random 24-byte nonce and manifest AAD:

```text
ASCII "CRROLL-MAN-V1\0"             14 bytes
canonical lowercase tripId           36 bytes
canonical lowercase assetId          36 bytes
keyEpoch uint32 big-endian             4 bytes
formatVersion uint32 big-endian        4 bytes
```

The canonical manifest AAD is exact 94-byte AAD: 14 domain bytes, 36 trip UUID bytes, 36 asset UUID bytes, 4 key-epoch bytes, and 4 format-version bytes.

The manifest plaintext schema and outer binary framing belong to `CON-002`; SEC-001 locks the key derivation, AEAD algorithm, nonce size, context, and AAD. The encrypted manifest is the trip-key wrap for the content root; v1 does not add a redundant nested wrapped-content-key object.

### Canonical media AAD

Every secretstream frame uses the same exact 95-byte AAD. Its domain is `CRROLL-AAD-V1\0`:

```text
ASCII "CRROLL-AAD-V1\0"             14 bytes
canonical lowercase tripId           36 bytes
canonical lowercase assetId          36 bytes
variant code                           1 byte   (PREVIEW = 1, ORIGINAL = 2)
keyEpoch uint32 big-endian             4 bytes  (1)
formatVersion uint32 big-endian        4 bytes  (1)
```

This preserves the accepted `AAD_FIELDS` order: `tripId`, `assetId`, `variant`, `keyEpoch`, `formatVersion`. The encoder parses and canonicalizes UUIDs before serialization. It rejects malformed UUIDs, unknown variants, unknown epochs, unknown formats, extra fields, and an incorrect byte length.

MIME type, filename, dimensions, capture metadata, and plaintext hash remain inside the encrypted manifest. The raw source-library identifier remains native-only and never enters the manifest or API. `sourceAssetKey` is the HMAC-derived opaque API/database dedupe value required by the locked data model; it is not media AAD, an object header, a log/metric label, or push data. The mobile plan's example that includes MIME and an asset idempotency/source key as AAD is stale and must not be implemented.

Secretstream uses 256 KiB plaintext frames, a terminal `TAG_FINAL`, and the same AAD on each push/pull. Frame order and the final tag remain mandatory. Exact framing, checksum fields, empty-file behavior, and golden bytes belong to `CON-002`.

## Native key ownership and state machine

### Command ownership

| Command                     | Security responsibility                                                                                                               | Explicit non-responsibility                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `ensureDeviceIdentity`      | Idempotently create/read device P-256 and X25519 public identity; private keys remain native                                          | Does not register with API or expose private bytes                                       |
| `createTripKey`             | For an owner with a known trip ID, idempotently create and securely persist a 24-hour provisional epoch-1 key                         | Does not return the key or an envelope and does not prove the server trip exists         |
| `discardProvisionalTripKey` | Idempotently erase only a still-provisional trip/epoch key after definitive create rejection or cancel-before-create                  | Must reject `INSTALLED`, `ACTIVE`, or `RETAINED`; never runs for an unknown HTTP outcome |
| `wrapTripKey`               | Seal the stored trip key to one exact recipient device/public-key version                                                             | Does not change membership or upload the envelope                                        |
| `importTripKey`             | Sole unwrap, context validation, idempotency check, secure persistence, same-device recovery, and provisional-owner confirmation path | Does not activate photo discovery or networking                                          |
| `activateTrip`              | Select a previously installed trip/epoch key, persist frozen activation metadata/baseline, and enable native scheduling               | Does not accept, decode, unwrap, import, or replace an envelope                          |
| `deactivateTrip`            | Stop discovery/scheduling and clear active selection                                                                                  | Does not erase a key before retention obligations finish                                 |

`importTripKey` is the only operation that unwraps, validates, persists, or recovers an envelope. `activateTrip` only selects an already-installed key and never accepts an envelope. `discardProvisionalTripKey` erases only `PROVISIONAL` epoch-1 material after a definitive failure or cancellation.

### Key states

```text
ABSENT --create(owner)--> PROVISIONAL --matching owner import--> INSTALLED
ABSENT --import(member or same-device recovery)-----------------> INSTALLED
PROVISIONAL --definitive failure/cancel or 24h GC--------------> DELETED
INSTALLED --activate--------------------------------------------> ACTIVE
ACTIVE --deactivate/logout--------------------------------------> INSTALLED
INSTALLED / ACTIVE --authenticated trip End---------------------> RETAINED
RETAINED --terminal cleanup-------------------------------------> DELETED
PROVISIONAL / INSTALLED / ACTIVE / RETAINED --irrecoverable identity/storage loss--> LOST
```

- `createTripKey` replay succeeds only while the same provisional/stored key exists; it never silently generates a replacement for a known trip/epoch record. If an owner's trip-key record is lost but the owner's X25519 private key survives, recovery uses the stored owner envelope through `importTripKey`.
- `discardProvisionalTripKey` and provisional GC compare state and epoch atomically; neither can erase a server-confirmed or active trip key.
- `activateTrip` from `ABSENT` or `LOST` returns a stable key blocker and performs no baseline, discovery, or network work.
- `importTripKey` may run before Start. Activation requires the server projection to show the membership/device/epoch frozen for the caller.
- `deactivateTrip` is an operational action, not cryptographic deletion or trip End. It returns the same frozen trip/epoch to `INSTALLED`, so same-account reauthentication may activate it again. Only an authenticated server trip-End projection moves `INSTALLED`/`ACTIVE` to non-reactivatable `RETAINED`.
- No command returns trip keys, content keys, derived keys, private keys, source HMAC keys, or decrypted manifests to JavaScript.

The accepted native TypeBox protocol currently carries `wrappedTripKey` on `activateTrip` even though it also exposes `importTripKey`, and it lacks `discardProvisionalTripKey`. The binding direction is to remove the activation envelope and add the narrow discard command in the downstream native-contract revision, not to give activation a second import path or let JS delete arbitrary keys.

## Secure-storage invariants

### iOS

- Generate the P-256 signing key in Secure Enclave where available; persist only its key reference with Keychain access control.
- Store X25519 secret, trip keys, source-ID HMAC key, and background bearer as separate Keychain records using `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`.
- Records are device-only, do not migrate to a different restored device, and are unavailable from reboot until the first user unlock. A background operation before first unlock reports `KEY_ACCESS_LOCKED` and performs no crypto/network work.
- Use an account/application access group scoped only to CrewRoll. Do not enable synchronizable/iCloud Keychain for these records.
- Ciphertext staging is app-private, excluded from backup, and uses `NSFileProtectionCompleteUntilFirstUserAuthentication`. The decrypted destination is also app-private/no-backup with `NSFileProtectionCompleteUntilFirstUserAuthentication`, matching the explicit after-first-unlock background-delivery contract; decryption is deferred before first unlock. Each plaintext destination carries a native-ledger expiry of creation plus 15 minutes, is deleted immediately after exact PhotoKit save or terminal failure, and is purged on the next launch/foreground/background reconciliation after a crash.

### Android

- Generate the P-256 signing key and a 256-bit AES-GCM KEK as non-exportable Android Keystore keys. Prefer hardware-backed/StrongBox protection when the device supports it; lack of StrongBox does not introduce a software crypto implementation outside Android Keystore.
- Generate X25519, trip, and source-HMAC secrets with libsodium and store only AES-GCM-wrapped records in credential-encrypted app-private storage. Each record uses a unique random 12-byte GCM nonce and AAD binding account namespace, key type, key ID, and version.
- Exclude the native ledger, wrapped-secret records, bearer records, and staging from Android backup and device-to-device transfer. Restored ciphertext without its non-exportable KEK is treated as `KEY_MATERIAL_LOST` and deleted.
- Do not run CrewRoll transfer work in Direct Boot or store secrets in device-protected storage. Before first unlock, reconciliation reports `KEY_ACCESS_LOCKED` and schedules no crypto/network work.
- Ciphertext and decrypted destinations use credential-encrypted, app-private, no-backup storage. A decrypted destination is created with owner-only permissions only after unlock, has a native-ledger expiry of creation plus 15 minutes, is deleted immediately after exact MediaStore save or terminal failure, and is purged on the next process start/foreground/worker reconciliation after a crash.

### Both platforms

- Secret records are namespaced by authenticated account and installation. A different signed-in account can never open a prior account's records.
- Native validates type, version, length, context, and authenticated storage metadata before using a key.
- Key bytes and separately materialized manifest fields have the shortest possible process lifetime and are overwritten where the language/runtime permits. They are never persisted in the ledger or an unprotected temp file; plaintext photo bytes exist only in the protected destination defined above.
- A background bearer is independently deletable/rotatable without changing E2EE identity.
- Simulator/emulator storage is test-only and cannot satisfy physical-device security acceptance.

## Deletion and retention invariants

| Trigger                                                      | Required action                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definitive create rejection or cancel before server creation | Call `discardProvisionalTripKey`; delete only `PROVISIONAL` epoch-1 material. A timeout/disconnect is not definitive and retains the key for idempotent retry. Native GC deletes any still-provisional record at 24 hours.                                                                     |
| User logout                                                  | Delete background bearer and deactivate scheduling. Keep account-namespaced E2EE/trip records quarantined only for same-account reauthentication; another account cannot access them.                                                                                                          |
| Explicit device removal/revocation or account purge          | Delete bearer, P-256 reference, X25519 secret, KEK/wrapped records, source-HMAC key, all trip keys, native ledger secrets, and staging on the cooperative device; revoke/delete server credentials and envelopes per server lifecycle.                                                         |
| Lobby cancellation                                           | Delete the local trip key and all server trip envelopes; no media should exist.                                                                                                                                                                                                                |
| Trip End                                                     | Stop discovering new photos, but retain the trip key while queued upload/download/save/receipt and reconciliation obligations remain. End alone is not a key-deletion event.                                                                                                                   |
| Trip `COMPLETE` and local queues terminal                    | Delete the local trip key, decrypted temp, content/derived keys, ciphertext staging no longer needed for retry, and encrypted manifest cache. Retain metadata-only history.                                                                                                                    |
| Immutable `hard_delete_at`                                   | On server, expire unresolved deliveries and purge remaining media objects, manifests, upload state, signed-URL capability, and trip-key envelopes. On each client, the next foreground/background reconciliation deletes the trip key and remaining staging even if completion was impossible. |
| Successful exact save                                        | Delete decrypted destination immediately; never delete the resulting system-library photo.                                                                                                                                                                                                     |
| Terminal decrypt/integrity failure                           | Delete any partial plaintext destination immediately; retain only the minimum ciphertext required by retry policy until hard expiry.                                                                                                                                                           |

S3 primary purge remains receipt-driven: after all required recipients have `SAVED_LOCALLY`, preview/original ciphertext is deleted idempotently. Hard expiry and the bucket lifecycle rule remain backstops. Server-side deletion cannot erase an offline device's local ciphertext/key or a user's system-library copy, so product language must not claim otherwise.

## Implementation and evidence boundary

This document binds the format and lifecycle but does not implement them. CON-002 owns the language-neutral media/manifest format, reference verifier, and canonical vectors. CON-003 owns exact HTTP/native TypeBox lengths and algorithm fields, client-supplied trip ID sequencing, pending-member key projection, activation shape, `discardProvisionalTripKey`, and stable key blockers. IOS-001/AND-001 own secure storage, crypto, protected staging, provisional GC, and physical-device lifecycle tests. SEC-001 does not change a contract, route, native engine, vector, serializer, or database.
