**Recommendation:** retain Cloudflare Workers, Hyperdrive/PostgreSQL, R2, and the durable native transfer engines. Fix recovery and lifecycle gaps first. Complete the asynchronous notification/cleanup pipeline using a managed queue before introducing a separate Node server or Redis. A queue can improve reliable dispatch and isolation; it cannot make an offline phone upload, override iOS scheduling, or certify that a photo reached the system photo library.

2. **CR-02 — Recover all blocked photos, including permission recovery. M. Confirmed retry gap.**
   Native engines skip persisted blocked work. “Sync now” only retries blocked items on the displayed 24-photo page/filter. A photo-permission blocker can clear that page, while “Try again” only refreshes reads. Add trip-wide re-evaluation and retry of recoverable work, independent of gallery paging.
   **Done when:** restoring permission/storage/network recovers a 100-photo backlog, including hidden and filtered items, without reinstalling or opening every page. Corrupt media, revoked devices, and expired work remain classified separately; no fake save receipts or duplicate library saves.
   Evidence: [page-scoped retry](/Users/uankit/Developer/personal/crewroll/src/bootstrap/ActiveTripTransfers.tsx:219), [permission handling](/Users/uankit/Developer/personal/crewroll/src/bootstrap/ActiveTripTransfers.tsx:143), [Android selection](/Users/uankit/Developer/personal/crewroll/modules/crewroll-transfer/android/src/main/java/com/uankit53/crewroll/transfer/media/NativePhotoTransferEngine.kt:141), [iOS selection](/Users/uankit/Developer/personal/crewroll/modules/crewroll-transfer/ios/IdentityKeys/Sources/CrewRollNativeKeys/MediaCrypto/ApplePhotoTransferEngine.swift:149).

3. **CR-03 — Resolve “trip ended” versus “still delivering” and new-trip eligibility. M/L. Confirmed behavior; product decision needed.**
   Ending stops capture, but completion waits for every active phone's final discovery pass. An unavailable phone can keep everyone in Finishing and hold the one-current-trip slot until the hard retention deadline. Existing expiry handling releases those slots and records incomplete delivery when cleanup runs. Choose an explicit earlier incomplete-resolution flow, or separate a finished capture session from the old delivery backlog and its slot. If allowing the next trip while old work drains, native storage/scheduling must support that deliberately.
   **Done when:** a lost/offline member does not force everyone to wait until the hard retention deadline to start another trip; incomplete delivery is never labeled complete. Cover host end, scheduled end, expiry, and pending uploads. Preserve the approved disabled buttons and the user's decision to remove “Leave now” after ending and the waiting tagline; do not simply restore those rejected elements.
   Evidence: [end transition](/Users/uankit/Developer/personal/crewroll/services/control-plane/src/db/trips/kyselyTripLifecycle.ts:181), [drain barrier](/Users/uankit/Developer/personal/crewroll/services/control-plane/src/db/trips/kyselyTripLifecycle.ts:203), [hard-expiry release](/Users/uankit/Developer/personal/crewroll/services/control-plane/src/db/trips/kyselyTripLifecycle.ts:444), [UI conditions](/Users/uankit/Developer/personal/crewroll/src/bootstrap/TripLifecycleControls.tsx:19).

4. **CR-04 — Keep cleanup progressing when one item fails. M. Confirmed failure coupling.**
   Trip expiry and ciphertext deletion run sequentially; one failure aborts the pass. Isolate individual failures, retain retryable work, and alert when an object remains beyond its purge deadline. A dead-letter entry must not mean the privacy deletion obligation is forgotten.
   **Done when:** a permanently failing object does not block unrelated deletions; transient failures recover; replay remains safe; overdue deletion is visible. Preserve the existing upload-expiry and PUT-versus-delete fences.
   Evidence: [cleanup loop](/Users/uankit/Developer/personal/crewroll/services/control-plane/src/db/media/kyselyMediaService.ts:929), [scheduled handler](/Users/uankit/Developer/personal/crewroll/services/control-plane/worker/index.ts:27).

5. **CR-05 — Measure real sync speed and make failures diagnosable. M. Confirmed observability gap.**
   HTTP duration logs exist, but there is no wired end-to-end latency/queue-age dashboard or alerting path in the inspected implementation. 14. **CR-14 — Profile and remove repeated server initialization/auth work. M. Performance candidate.**
    Each fetch creates the request runtime, whose token-verifier factory creates a new remote JWKS resolver. Its ten-minute object cache consequently cannot persist between request runtimes. Continue verifying every token; never cache authorization decisions across accounts. Keep DB connections and request actors scoped correctly.
    **Done when:** warm requests avoid redundant key retrieval without weakening key rotation, issuer validation, or isolation; record p50/p95 before/after. Do not replace the already-shared Fastify schema setup or introduce a global PostgreSQL pool without evidence.

22. **CR-22 — Shorten media transaction lifetimes and scale cleanup with fair claims. L. Confirmed contention paths; impact unmeasured.**

**Queue/framework decision**

| Choice                                                       | Fit for CrewRoll                                                                                                                                                 | Recommendation                                                                                                                  |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Keep only the present cron and polling                       | Simple, but no completed push/outbox dispatcher; weak failure isolation and backlog observability.                                                               | Stabilize it immediately, but do not call the missing job pipeline production-ready.                                            |
| Cloudflare Queues + a consumer Worker + transactional outbox | Fits existing hosting; separates push/cleanup execution without operating a VM or Redis.                                                                         | Preferred implementation candidate for CR-11/22. Configure batch delay for the required latency rather than accepting defaults. |
| pg-boss + an explicitly deployed Node worker                 | PostgreSQL-based job library; already installed, currently unused. Would require a running worker, deployment/health/retry ownership, and DB-capacity budgeting. | Valid alternative if a Node service is intentionally needed. It is not already active just because it is in package.json.       |
| BullMQ + Redis + Node workers                                | Adds Redis and another operating model.                                                                                                                          | Defer unless measured needs or another service justify that infrastructure.                                                     |
| Move the API to a dedicated server / rewrite Fastify         | No current capacity measurements demonstrate a need.                                                                                                             | Defer. First measure queue age, phone scheduling, auth fetches, SQL/lock waits, and transfer bytes.                             |

Cloudflare Queues provides at-least-once delivery, so consumers still need deduplication. Explicitly configure retries and a dead-letter queue; exhausted messages can otherwise be discarded. Preserve per-trip ordering through server sequence/version checks rather than assuming queue delivery order. [Delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/), [retries and batching](https://developers.cloudflare.com/queues/configuration/batching-retries/), [dead-letter behavior](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/). pg-boss supports PostgreSQL-backed workers and retry handling; BullMQ is a Redis-backed Node queue. [pg-boss workers](https://pgboss.io/api/workers), [BullMQ overview](https://docs.bullmq.io/).

Proposed event path: **database transaction writes delivery/inbox + outbox → publisher hands off to managed queue → consumer sends a coalesced wake hint → phone reconciles authoritative state → encrypted R2 transfer → verified local save → receipt**. Mark outbox handoff only after queue acceptance; tolerate a crash between enqueue and that acknowledgement. Retain a repair sweep for unpublished events and stuck jobs. Separate cleanup jobs from notification jobs so provider trouble cannot block deletion. Photo bytes remain encrypted and go through the media transfer path, not inside queue messages.

Push cannot guarantee instant background execution. Apple's delivery policy can delay or discard background notifications, so a polling/reconciliation fallback remains required. [Apple background notification guidance](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app).

**Suggested implementation sequence**

1. Ship the small Sign out entry while fixing trip-wide retry and the ended/finishing policy; instrument those paths. Harden cleanup immediately in parallel.
2. Run the physical two-/three-phone flows and collect stage timings. Keep each flow complete and reviewable before moving on.
3. Complete production separation, account/privacy controls, limits, and release gates before expanding access substantially.
4. Implement the managed dispatch/push pipeline, adaptive polling, and measured background scheduling/transfer improvements.
5. Use the resulting measurements to choose database/native persistence tuning, then build archived galleries, richer browsing, and profile polish.
